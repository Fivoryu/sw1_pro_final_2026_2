# RoomForge — primer corte SaaS con login del panel

## Objetivo y autorización

Construir desde cero la base de identidad para el panel web de RoomForge: acceso seguro para administrador de plataforma, administrador de inmobiliaria y agente; el cliente móvil se aborda después. La autorización deriva de las decisiones explícitas del usuario en esta sesión: panel SaaS primero, invitación inicial por correo y TDD estricto.

Este es el primer corte de un SaaS incremental, no la implementación completa del catálogo, publicaciones, captura 3D ni reservas.

## Decisiones de alcance vigentes

- Panel web inicial para `platform_admin`, `agency_admin` y `agent`; el cliente queda fuera de este corte.
- La primera cuenta de administrador de plataforma se inicia mediante una invitación por correo de un solo uso emitida por un comando local/de despliegue, sin endpoint público de bootstrap. No se envían contraseñas.
- Usar FastAPI, PostgreSQL/Alembic y React + TypeScript + Vite, en continuidad con la topología documentada y README del proyecto. No recuperar el código eliminado.
- Mantener las decisiones de seguridad previamente aceptadas que no contradicen la redefinición: Argon2id; access JWT corto y refresh opaco rotatorio; rol y tenant resueltos por el servidor; TOTP obligatorio para administradores de plataforma e inmobiliaria con códigos de recuperación de un solo uso; sesión administrativa revocada tras 30 minutos de inactividad.
- Presupuesto: gastar lo mínimo posible. No incorporar servicios, licencias, APIs o infraestructura paga ni crear recursos facturables nuevos para este corte. Reutilizar componentes libres donde corresponda. R6 usó exclusivamente la instancia PostgreSQL nueva, aislada y desechable expresamente autorizada; no se presumió ni reutilizó una base existente. No desplegar a AWS ni asumir que los créditos informados están disponibles.
- El correo se abstraerá detrás de un adaptador configurable, sin fijar ni contratar proveedor externo ni guardar credenciales en Git. Las pruebas usarán un emisor falso; envío real queda pendiente de un transporte ya disponible o de una decisión explícita compatible con el presupuesto.
- El administrador debe enrolar y verificar TOTP antes de habilitar su primera sesión; cada login administrativo requiere TOTP o un código de recuperación de un solo uso. Mostrar códigos de recuperación una sola vez y persistir solo hashes.
- La web no debe persistir access ni refresh tokens en almacenamiento web: entregar refresh mediante cookie `HttpOnly` con validación de origen/CSRF y mantener el access token solo en memoria. Para restaurar sesión, guardar únicamente el CSRF en `sessionStorage` limitado a la pestaña; al recargar, usar ese CSRF y la cookie `HttpOnly` en `/refresh`, guardar el CSRF rotado y resolver identidad con `/me`. Limpiar el CSRF al cerrar sesión o si falla la restauración.
- No incluir todavía CRUD de agencias, publicaciones, catálogo, reconstrucción 3D, reservas, pagos, suscripciones ni blockchain. Esta etapa entrega identidad/invitación y una carcasa de panel protegida por rol.

## Criterios de aceptación

1. No existe endpoint público de autorregistro/bootstrap; un comando de operador local/de despliegue envía una invitación inicial de un solo uso al administrador de plataforma. La administración de agencias queda para un corte posterior.
2. El administrador enrola y verifica TOTP antes de su primera sesión; cada login admin requiere TOTP o un código de recuperación no reutilizable. Los códigos se muestran una vez y solo se persisten hasheados.
3. El backend resuelve identidad, rol y contexto tenant desde datos autenticados; no confía en rol o `tenant_id` enviados por el navegador.
4. Los refresh tokens se rotan y revocan al cerrar sesión; el browser los recibe solo en cookie `HttpOnly` protegida por validación de origen/CSRF. No se almacenan access ni refresh tokens en almacenamiento web; el access token permanece en memoria y solo el CSRF se conserva en `sessionStorage` de la pestaña para restaurar sesión.
5. El panel protege sus rutas, muestra estado/carga/error accesibles y no presenta funciones fuera del alcance de este corte como implementadas.
6. Las pruebas TDD demuestran RED antes de la implementación de cada comportamiento y GREEN/refactor posterior; runners, versiones disponibles y resultados quedan anotados.
7. La verificación fue aditiva: no se modificaron datos ni se tocaron servicios/volúmenes existentes de PostgreSQL/Floci. R6 usó solo una instancia local nueva, temporal y aislada, con contenedor único, puerto aleatorio enlazado a loopback y sin volumen Docker persistente; migración y concurrencia pasaron 2/2. Un intento abortado podría haber dejado un volumen anónimo que no puede atribuirse con la evidencia disponible; no ejecutar prune ni eliminar volúmenes sin atribución.
8. No se crean costos recurrentes ni infraestructura facturable; cualquier necesidad de un servicio externo queda reportada y no se activa sin confirmación.
9. Un administrador puede reemitir de forma segura la invitación inicial cuando el token o el enrollment challenge anterior expiró; los tokens anteriores quedan inutilizables.
10. Dos intentos concurrentes de consumir el mismo código no pueden tener éxito a la vez. La prueba SQLite observó un HTTP 500 `SQLITE_LOCKED` para el perdedor y acepta cualquier respuesta no-200. R6 verificó además el flujo HTTP en PostgreSQL temporal aislada: una solicitud exitosa, una rechazada, una sesión y un código consumido; 2/2 pruebas focalizadas (migración y concurrencia) aprobadas. El downgrade de Alembic no se probó.

## Ruta y estrategia

- **Ruta general:** ODD; el usuario no seleccionó SDD/OpenSpec. El mapeo de 4+ archivos se delegó a `gentle-ai-explore`; la escritura multiarchivo se delegará a un escritor por tarea; los comandos de verificación se delegarán de acuerdo con la regla RDD-aware.
- **RDD:** apagado según el estado inyectado al iniciar la sesión; no iniciar revisión nativa mientras siga apagado.
- **Entrega:** `ask-on-risk`; forecast inicial aproximado de 700–1.000 líneas autoradas entre código y pruebas, dividido por backend y panel para mantener unidades revisables. No se crea PR ni se publica. Los commits quedan pendientes de autorización explícita, conforme a las reglas del repositorio.
