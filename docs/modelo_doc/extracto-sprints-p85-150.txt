PROCESO DE DESARROLLO SCRUM

CAPITULO 1 ­ REQUERIMENTOS (Sprint 0)

1. Propósito
El propósito del Sprint 0 es establecer la base inicial del proyecto mediante la identificación,
análisis y organización de los requerimientos necesarios para el desarrollo de la Plataforma
Inteligente de Seguimiento Operativo y Productividad en Trabajo Remoto.

En esta etapa se define el alcance general del sistema, los objetivos del producto, los actores
principales, las funcionalidades iniciales, el Product Backlog, la planificación de los Sprints, los
criterios de calidad y la infraestructura tecnológica requerida para el desarrollo. Este Sprint
permite preparar el trabajo técnico y documental antes de iniciar la implementación de las
funcionalidades principales.

Asimismo, el Sprint 0 permite al equipo SCRUM comprender el problema que se desea
resolver y organizar el desarrollo de los componentes principales del sistema: la aplicación de
escritorio para el trabajador remoto, el panel administrativo web para supervisores y
administradores, y el backend/API encargado de centralizar la lógica de negocio, la
autenticación, la persistencia de datos y la comunicación entre módulos.

De esta manera, el Sprint 0 constituye la etapa de preparación del proyecto, donde se
consolidan los requerimientos, se estructuran las historias de usuario y se dejan definidas las
condiciones necesarias para iniciar el Sprint 1 con una base clara, ordenada y coherente.

2. Ámbito del sistema
El sistema estará orientado al registro, monitoreo y análisis de la actividad laboral de
trabajadores remotos, mediante una plataforma integrada compuesta por una aplicación de
escritorio, un panel administrativo web, un backend/API y una base de datos centralizada. Su
finalidad es brindar trazabilidad operativa sobre la jornada laboral, el uso de herramientas de
trabajo, los periodos de inactividad, los eventos relevantes y la comunicación entre
trabajadores, supervisores y administradores.

                                                                                                              85
La aplicación de escritorio estará dirigida al trabajador remoto y permitirá iniciar sesión,
registrar el inicio, pausa, reanudación y finalización de la jornada laboral. Además, permitirá
monitorear aplicaciones activas, registrar navegación autorizada durante la jornada, detectar
periodos de inactividad, mostrar notificaciones y facilitar la comunicación operativa con
supervisores mediante mecanismos integrados al sistema.

El panel administrativo web estará dirigido a administradores y supervisores. Desde este
componente será posible gestionar usuarios, roles y permisos, configurar jornadas laborales,
visualizar el estado actual de los trabajadores, consultar dashboards, revisar reportes, analizar
aplicaciones utilizadas, consultar historial de navegación, verificar periodos de inactividad,
revisar alertas y acceder a información consolidada para apoyar la toma de decisiones.

El backend/API será el componente encargado de centralizar la lógica de negocio del sistema,
gestionar la autenticación, aplicar permisos por rol, recibir la información enviada desde la
aplicación de escritorio, almacenar los registros en la base de datos y proporcionar los
servicios necesarios para que el panel web pueda consultar y representar la información de
forma organizada.

El ámbito del sistema comprende los módulos de autenticación, administración de usuarios y
roles, control de jornada, monitoreo de actividad, registro de navegación, detección de
inactividad, productividad, notificaciones, bitácora administrativa, reportes, dashboards,
alertas y comunicación operativa. Las funcionalidades relacionadas con cámara, registro de
voz o visualización de ubicación se consideran módulos avanzados u opcionales, sujetos a
disponibilidad técnica, consentimiento del trabajador y políticas internas de la organización.

    1. Objetivo del producto
Desarrollar una Plataforma Inteligente de Seguimiento Operativo y Productividad en Trabajo
Remoto, compuesta por una aplicación de escritorio para trabajadores, un panel
administrativo web para supervisores y administradores, y un backend/API centralizado que
permita registrar, monitorear, almacenar y analizar la actividad laboral durante la jornada de
trabajo.

                                                                                                              86
El producto tiene como objetivo brindar trazabilidad operativa sobre el cumplimiento de
jornadas, el uso de aplicaciones, la navegación autorizada, los periodos de inactividad, las
alertas generadas, las evidencias registradas y la comunicación operativa entre los usuarios
del sistema.

De esta manera, la plataforma busca apoyar a las organizaciones en la supervisión del trabajo
remoto, facilitando el seguimiento de actividades, la generación de reportes, la identificación
de eventos relevantes y la toma de decisiones basada en información objetiva, segura y
organizada.

    2. Descripción general del producto
El producto consiste en una plataforma tecnológica orientada a fortalecer la supervisión,
trazabilidad y análisis de la productividad en el trabajo remoto dentro de una organización.
La solución está compuesta por una aplicación de escritorio instalada en el equipo del
trabajador, un panel administrativo web utilizado por supervisores y administradores, un
backend/API encargado de centralizar la lógica del sistema y una base de datos para
almacenar la información generada durante la jornada laboral.

La aplicación de escritorio permitirá al trabajador iniciar sesión y registrar su jornada laboral,
incluyendo inicio, pausa, reanudación y cierre. Durante la jornada, el sistema podrá detectar
la aplicación activa en uso, registrar el tiempo utilizado por aplicación, identificar sitios o
dominios visitados en navegadores autorizados, detectar periodos de inactividad y recibir
notificaciones operativas enviadas desde el sistema. Este componente funcionará como
agente de monitoreo, enviando información al backend de manera controlada y asociada al
usuario correspondiente.

El panel administrativo web permitirá centralizar y visualizar la información capturada por la
aplicación de escritorio. Desde este panel, los supervisores y administradores podrán
consultar dashboards, gráficos, reportes, historial de jornadas, aplicaciones utilizadas,
navegación registrada, periodos de inactividad, estado actual de los trabajadores, bitácora
administrativa y notificaciones. Además, podrán gestionar usuarios, roles, permisos, jornadas
laborales y configuraciones necesarias para el funcionamiento de la plataforma.

                                                                                                              87
El backend/API será responsable de recibir, validar, procesar y almacenar la información
proveniente de la aplicación de escritorio, así como de proporcionar los servicios que
consume el panel administrativo web. Este componente también gestionará la autenticación,
los permisos por rol, la lógica de negocio, la comunicación entre módulos y la persistencia de
datos en la base de datos PostgreSQL.

El sistema busca mejorar el control operativo del trabajo remoto, proporcionar información
objetiva sobre la actividad laboral, facilitar la detección de desviaciones, apoyar la toma de
decisiones y fortalecer la comunicación entre supervisores y trabajadores. Las
funcionalidades de evidencias por captura, cámara, ubicación o registro de voz serán tratadas
como módulos avanzados, sujetos a consentimiento, políticas internas de la organización y
criterios de seguridad y privacidad.

    4. Requerimientos iniciales
A partir del análisis del problema, las necesidades del entorno de trabajo remoto y la
definición inicial del Product Backlog, se identificaron los requerimientos centrales que el
sistema debe satisfacer. Estos requerimientos permiten establecer una base funcional para el
desarrollo de la plataforma y sirven como guía para organizar las historias de usuario, los
módulos del sistema y los Sprints posteriores.

    4.1. Necesidades identificadas
    1. Control de jornada laboral: Las organizaciones requieren un mecanismo

         automatizado para registrar el inicio, pausa, reanudación y finalización de la jornada
         de cada trabajador remoto, reduciendo la dependencia de reportes manuales.
    2. Visibilidad de la actividad laboral: Los supervisores necesitan consultar qué
         aplicaciones utilizan los trabajadores, qué sitios o dominios visitan durante la jornada
         y cuál es su estado operativo.
    3. Detección de inactividad: Es necesario identificar automáticamente los períodos en
         los que el trabajador no interactúa con el teclado o el ratón, con el fin de diferenciar
         tiempos activos e inactivos.
    4. Registro de eventos y evidencias: Ante eventos relevantes o sospechosos definidos
         por reglas del sistema, la plataforma debe registrar información asociada al usuario,

                                                                                                              90
         jornada, fecha, hora y tipo de evento. Las evidencias visuales o capturas solo deberán
         gestionarse bajo autorización y políticas internas de la organización.
    5. Centralización de la información: Toda la información generada por la aplicación de
         escritorio debe consolidarse en un sistema centralizado, accesible desde el panel web,
         para que administradores y supervisores puedan analizar datos actuales e históricos.
    6. Comunicación interna: Se necesita un canal de comunicación operativo entre
         supervisores y trabajadores para enviar avisos, instrucciones o notificaciones sin
         depender únicamente de herramientas externas.
    7. Gestión de acceso segura: El sistema debe permitir el acceso únicamente a usuarios
         autorizados, diferenciando permisos según el rol asignado: owner, administrador,
         supervisor o trabajador.
    8. Trazabilidad de acciones: Las operaciones administrativas relevantes deben quedar
         registradas en una bitácora, permitiendo auditoría y control interno sobre las acciones
         realizadas en el sistema.

    4.2. Requerimientos generales del sistema
El sistema por desarrollar, denominado "Plataforma Inteligente de Seguimiento Operativo y
Productividad en Trabajo Remoto", se compone de varios componentes integrados que
trabajan de forma coordinada:

    · Aplicación de escritorio: agente instalado en el equipo del trabajador, desarrollado
         con Electron, Vite y TypeScript. Este componente permite iniciar sesión, registrar la
         jornada laboral, detectar actividad del sistema, registrar aplicaciones activas,
         identificar periodos de inactividad, capturar navegación autorizada y comunicarse con
         el backend.

    · Panel administrativo web: interfaz desarrollada con React, Vite, TypeScript y Tailwind
         CSS. Está dirigida a administradores y supervisores, permitiendo gestionar usuarios,
         roles, jornadas, reportes, dashboards, navegación, aplicaciones, productividad,
         inactividad, notificaciones y bitácora administrativa.

    · Backend/API: componente desarrollado con Django y Django REST Framework. Es
         responsable de centralizar la lógica de negocio, gestionar autenticación, aplicar

                                                                                                              91
    permisos, recibir información desde la aplicación de escritorio, atender las peticiones
    del panel web y mantener la comunicación entre los módulos del sistema.
· Base de datos: sistema de persistencia implementado en PostgreSQL, encargado de
    almacenar usuarios, roles, jornadas, eventos, aplicaciones, navegación, inactividad,
    notificaciones, bitácora administrativa y demás registros operativos del sistema.

Ambos clientes, la aplicación de escritorio y el panel web, se comunican con el backend
mediante servicios API REST, utilizando autenticación basada en tokens JWT y mecanismos
de control de acceso según el rol del usuario.

4.5. Reglas de negocio iniciales

1. Unicidad de jornada: Un trabajador no puede tener dos jornadas activas
    simultáneamente. Para iniciar una nueva jornada, la anterior debe estar cerrada.

2. Tolerancia de horario: El sistema podrá considerar como "fuera de horario" a un
    trabajador que no inicie su jornada dentro del margen de tolerancia definido en la
    configuración correspondiente.

3. Clasificación de aplicaciones: Las aplicaciones detectadas se clasificarán inicialmente
    como neutras. Posteriormente, el administrador o supervisor podrá clasificarlas como
    productivas, neutras o no laborales.

                                                 94
4. Cálculo de productividad: El sistema calculará la productividad considerando el
    tiempo asociado a aplicaciones productivas frente al tiempo total de jornada,
    inactividad y uso de aplicaciones no laborales.

5. Registro de eventos sospechosos: Se considerará evento sospechoso la combinación
    de condiciones definidas por el sistema, como inactividad prolongada y uso de
    aplicaciones clasificadas como no laborales.

6. Gestión de evidencias: Las evidencias visuales, capturas o registros relacionados con
    cámara deberán generarse únicamente bajo autorización y de acuerdo con las
    políticas internas de la organización.

7. Privacidad y consentimiento: Antes de iniciar el monitoreo, el trabajador debe
    conocer qué datos serán recolectados, con qué finalidad y bajo qué condiciones serán
    utilizados.

8. Eliminación de usuarios: No se deberá eliminar definitivamente un usuario que tenga
    registros de jornada, eventos, navegación, inactividad, mensajes o bitácora asociada.
    En su lugar, el sistema deberá permitir su desactivación.

    7. Casos de uso

Los casos de uso permiten representar las principales interacciones entre los actores del
sistema y las funcionalidades de la Plataforma Inteligente de Seguimiento Operativo y
Productividad en Trabajo Remoto. A través de estos casos se identifican las acciones que
pueden realizar los usuarios según su rol, así como los procesos automáticos que ejecuta el
sistema durante la jornada laboral.

Para mantener una mejor organización, los casos de uso se agrupan en seis paquetes
funcionales. Cada paquete representa un conjunto de funcionalidades relacionadas, lo que
permite ordenar el sistema por áreas de responsabilidad y facilitar la elaboración de los
diagramas UML.

    8. Planificación de Sprints

La planificación de Sprints permite organizar el desarrollo del sistema en incrementos
funcionales, siguiendo un avance progresivo y coherente con la prioridad de los
requerimientos definidos en el Product Backlog. Para este proyecto se definieron tres Sprints
principales, además del Sprint 0 utilizado para la planificación, preparación del entorno,
definición inicial del producto, organización documental y diseño preliminar de la solución.

Cada Sprint concentra un bloque funcional del sistema, evitando mezclar funcionalidades
base con módulos avanzados que dependen de procesos previos. De esta manera, el
desarrollo avanza de forma incremental: primero se construye la base administrativa y el
control de jornada; luego se implementa el monitoreo de actividad del trabajador; y
finalmente se integran reportes, alertas, evidencias, comunicación operativa y funciones
avanzadas.

La distribución se realiza tomando como base los 46 elementos del Product Backlog. El Sprint
1 agrupa 10 elementos orientados a autenticación, administración y jornada laboral. El Sprint
2 concentra 17 elementos relacionados con monitoreo de aplicaciones, navegación,
inactividad y productividad. El Sprint 3 agrupa 19 elementos vinculados con eventos,
evidencias, alertas, dashboard, reportes, comunicación, ubicación y funciones avanzadas.
Esta organización permite mantener una entrega progresiva, verificable y alineada con las
dependencias funcionales del sistema.

    8.1. Duración de los Sprints

Cada Sprint tendrá una duración aproximada de 21 días calendario, siguiendo un ciclo de
trabajo que incluye planificación, desarrollo, revisión y retrospectiva. El Sprint 0 se considera
una fase inicial de preparación del proyecto, por lo que tiene una duración ligeramente mayor
debido a la definición documental, técnica y organizativa.

    10. Patrón de desarrollo

El patrón de desarrollo define la forma en que el equipo organizará las actividades técnicas
durante los Sprints, estableciendo una guía común para el análisis, diseño, implementación,
pruebas, integración y documentación del sistema. Para este proyecto se adopta un enfoque
incremental e iterativo, donde cada Sprint agrega nuevas funcionalidades sobre una base
previamente construida.

La Plataforma Inteligente de Seguimiento Operativo y Productividad en Trabajo Remoto
requiere una organización modular, debido a que está compuesta por una aplicación de
escritorio, un panel administrativo web, un backend/API y una base de datos centralizada.
Por esta razón, el desarrollo se estructura en componentes separados, pero integrados
mediante servicios API y mecanismos de comunicación cliente-servidor.

Los modelos iniciales permiten representar de manera gráfica y conceptual la estructura
general del sistema antes de iniciar la implementación completa de las funcionalidades. Estos
modelos forman parte del Sprint 0, ya que ayudan al equipo SCRUM a comprender el alcance

En esta sección se presentan los modelos preliminares de contexto, casos de uso, datos,
arquitectura e interfaces principales de la Plataforma Inteligente de Seguimiento Operativo y
Productividad en Trabajo Remoto.

    11.1. Modelo de contexto
El modelo de contexto muestra la relación general entre los actores externos y la plataforma.
En este modelo se identifica cómo interactúan los trabajadores, supervisores,
administradores y owner con los principales componentes del sistema.
El trabajador interactúa principalmente con la aplicación de escritorio, desde donde registra
su jornada laboral, recibe notificaciones y genera información operativa relacionada con
aplicaciones, navegación e inactividad. El supervisor y el administrador interactúan con el
panel administrativo web, desde donde pueden consultar información, gestionar usuarios,
revisar reportes, visualizar estados y configurar aspectos operativos del sistema.
El backend/API actúa como componente central, recibiendo la información enviada desde la
aplicación de escritorio, procesando solicitudes del panel web y almacenando los datos en la
base de datos PostgreSQL.

    11.2. Modelo de casos de uso
El modelo de casos de uso representa las funcionalidades principales que ofrece el sistema a
cada tipo de actor. Para mantener el orden del modelo, los casos de uso se agrupan en seis
paquetes funcionales:

    · Autenticación y administración.
    · Jornada laboral y estado operativo.
    · Monitoreo de actividad.
    · Supervisión y productividad.
    · Eventos, evidencias y alertas.
    · Dashboard, reportes y comunicación operativa.
Los actores principales identificados son Owner, Administrador, Supervisor, Trabajador y
Sistema. El actor Sistema representa los procesos automáticos ejecutados por la plataforma,
como clasificación de aplicaciones, detección de inactividad, cálculo de productividad,
registro de eventos y generación de alertas.

    11.4. Modelo de arquitectura inicial
El modelo de arquitectura inicial representa la organización técnica de la plataforma. El
sistema se estructura mediante una arquitectura cliente-servidor, donde la aplicación de
escritorio y el panel administrativo web consumen servicios proporcionados por el
backend/API.
La aplicación de escritorio, desarrollada con Electron, Vite y TypeScript, se ejecuta en el
equipo del trabajador y se encarga de registrar jornada, detectar actividad del equipo y enviar
eventos al backend. El panel administrativo web, desarrollado con React, Vite, TypeScript y
Tailwind CSS, permite a supervisores y administradores consultar y gestionar la información
del sistema. El backend/API, desarrollado con Django y Django REST Framework, centraliza la
lógica de negocio, autenticación, permisos y acceso a datos. La base de datos PostgreSQL
almacena toda la información persistente de la plataforma.

    13. Conclusión del Sprint 0
El Sprint 0 permitió establecer la base inicial del proyecto "Plataforma Inteligente de
Seguimiento Operativo y Productividad en Trabajo Remoto". Durante esta etapa se realizó la
definición del alcance del sistema, la identificación de actores, la organización de
requerimientos, la elaboración del Product Backlog, la planificación de Sprints, la selección de
tecnologías, la definición del patrón de desarrollo, la elaboración de modelos iniciales y la
formulación de criterios de calidad.

Como resultado de este Sprint, el equipo logró comprender con mayor claridad el problema
que se busca resolver y la solución tecnológica propuesta. Se identificó la necesidad de contar
con una plataforma que permita registrar jornadas laborales, monitorear actividad del
trabajador remoto, detectar inactividad, consultar aplicaciones utilizadas, registrar
navegación autorizada, generar reportes, gestionar alertas y facilitar la comunicación
operativa entre supervisores y trabajadores.

También se definieron los componentes principales del sistema: una aplicación de escritorio
para el trabajador, un panel administrativo web para supervisores y administradores, un
backend/API encargado de centralizar la lógica del sistema y una base de datos PostgreSQL
para almacenar la información operativa. Esta división permite organizar el desarrollo de
manera modular y facilita la integración progresiva de funcionalidades durante los siguientes
Sprints.

El Product Backlog quedó estructurado con 46 elementos, distribuidos de forma incremental
en tres Sprints principales. El Sprint 1 se orienta a la base administrativa, autenticación,
usuarios, roles y control de jornada. El Sprint 2 se enfoca en el monitoreo de actividad,
navegación, inactividad y productividad. El Sprint 3 agrupa reportes, alertas, evidencias,

comunicación operativa y funciones avanzadas como ubicación referencial o cámara, siempre
considerando criterios de autorización, privacidad y consentimiento.
Asimismo, se definieron modelos iniciales que sirven como guía para el desarrollo del sistema,
entre ellos el modelo de contexto, modelo de casos de uso por paquetes funcionales, modelo
inicial de datos, modelo de arquitectura y esbozos de interfaces principales. Estos modelos
permiten visualizar la estructura general de la solución y facilitan la comunicación entre los
integrantes del equipo.
En conclusión, el Sprint 0 cumplió su propósito de preparar el proyecto antes de iniciar la
implementación. La documentación generada en esta etapa proporciona una base clara,
ordenada y coherente para comenzar el Sprint 1, reduciendo ambigüedades y estableciendo
una guía de trabajo para el análisis, diseño, desarrollo, pruebas e integración de la plataforma.
